Agent Product Planning Playbook

Agent 产品规划方法论

这不是某一个功能的需求文档，而是一套可以反复套用的任务节点拆解模板：规划任何新的 Agent 功能时，先别画页面原型，先把用户的一次请求拆成一条节点链——每个节点标清楚是"调用 Skill/Tool"还是"大模型通用能力"，哪些节点必须停下来给用户确认。以掌术 AI 科研工作站的 7 条真实任务链路作为示范。

5 步拆解法 3 种节点类型 R0–R3 风险分级 7 条示范链路

1为什么旧思路不适用

传统互联网产品经理的训练，是围绕"页面—按钮—交互路径"展开的。Agent 产品没有固定页面流程，用户一句话背后是一条动态生成的任务链——规划单位、关注重点、需求文档形态都要换一套。

传统互联网产品经理

  • 按页面 / 功能点 / 按钮拆需求
  • 关注交互路径、UI 布局、埋点方案
  • 需求文档 = 原型图 + 交互说明 + 字段表
  • "完成"＝页面能跑通、按钮能点通
  • 风险管理靠前端校验、登录权限拦截
  • 复用靠组件库、页面模板
VS

Agent 产品经理

  • 按任务节点 / 状态流转拆需求
  • 关注每个节点该由 Skill 还是大模型完成
  • 需求文档 = 任务链路图 + 节点能力归属 + 确认点设计
  • "完成"＝结果真实可信、可复现、该确认的都确认了
  • 风险管理靠 R0～R3 分级，明确暂停确认的节点
  • 复用靠 Skill/Tool——同一能力服务多条任务链路

2拆解方法：5 步法

规划任何一个新的 Agent 功能，都按这 5 步走一遍，不要先画原型图。

01

先定意图边界，不定页面边界

一条任务链路对应一个明确的用户意图起点和终点，不是一个页面或一次点击。先问："用户带着什么问题进来，带着什么结果离开？"

02

逐节点拆解状态流转

每一步问"发生了什么状态变化"，而不是"用户点了哪个按钮"。状态变化是任务链路的最小单位。

03

给每个节点归属能力

能不能靠大模型通用能力直接完成？涉及真实数据、精确计算、外部系统交互，就必须走 Skill/Tool（判断标准见下一节）。

04

标出确认点（R0～R3）

哪些节点的结果会影响正式决策、或者不可逆，必须停下来让用户确认；哪些只是解释性内容，不需要确认。

05

复用已有 Skill，而非重新造页面

检查任务链路里需要的能力是否已有 Skill 可复用，而不是习惯性地要求前后端另起一套页面流程。

3节点类型判断标准

每个节点只能是这三种之一。判断错了，要么会让大模型编造数据，要么会让工程资源浪费在不需要 Skill 的地方。

LLM

大模型通用能力

  • 纯语言理解、总结、翻译、解释
  • 基于已有材料做综合、创意生成
  • 不需要访问真实数据或外部系统
  • 结果允许一定程度的表述差异
常见误判把"生成图表"当成 LLM 能力——即使模型"看起来会画"，图表必须用真实数据渲染，这一步该是 Skill。
SKL

Skill / Tool 调用

  • 需要访问真实数据、数据库或外部系统
  • 需要精确计算，结果必须可复现
  • 产出正式数字、统计结果、正式文件
  • 需要对照事实做校验（防止大模型编造）
常见误判把"解释一个统计学概念"也算成 Skill——不需要访问任何系统，纯知识问答，这一步该是 LLM。
R?

用户确认点

  • 结果会影响正式研究/业务决策
  • 动作不可逆，或涉及正式对外发布
  • R1：方向性确认；R2：影响决策路径；R3：正式产物/外部动作
  • 不管内容是 Skill 产出还是 LLM 生成，同样要停下来
常见误判把每一步都设成确认点——只读解释类内容（R0）不需要确认，过度确认会拖垮体验。

6进阶：容易被忽略的 5 件事

前面的模板和示例都是"成功路径"。真正落地时，以下 5 件事是专业 Agent 产品设计里最容易被漏掉、但出问题时代价最大的部分。

01

失败和拒绝路径不能省

每条链路画完"成功路径"后，至少要问：Skill 调用失败/返回空结果怎么办？用户在确认点回答"不满意"怎么办？退回到哪个节点重新执行，而不是中断或卡死——本文档的 3 个示例都补了这类分支标注（⚠ / ↩ 开头的行）。

02

能力范围和工具访问权限要解耦

"用户能不能用某个能力包（Skill 的场景化组合）"和"这次对话能调用哪些底层工具"，是两个独立的问题，不要用同一个开关控制。一旦耦合，一份可以被普通用户上传/编辑的场景化内容，就可能意外获得控制系统实际可调用工具集的能力——工具访问权限应该由会话/身份层面的配置决定，能力包只负责往 Prompt 里加引导内容。

03

节点级可观测性，不是页面埋点

老产品经理埋点埋在按钮点击上；Agent 产品经理要埋在任务节点上——每个节点的成功率、耗时、失败原因，才能定位"链路经常卡在哪一步"，而不是只知道"用户流失了"。

04

该并行就并行，别硬串成一条线

链路里如果有几个节点互相独立（比如同时查文献 + 查数据集、同时验证多个候选方案），应该拆给并行子任务执行（Coordinator 派发给多个 Worker），而不是逼大模型排队一步步等，白白拉长响应时间。

05

留意每个节点的成本和延迟

Skill 调用有的很贵（真实计算、多轮检索、外部 API），LLM 节点有的很便宜（一次总结）；确认点天然是异步断点，不用为了"体验流畅"把所有节点都做成同步阻塞等待，可以让用户先去做别的事，结果出来再通知。

7上线前自查清单

功能规划定稿前，对照这份清单逐条检查。

能不能走纯 LLM，看有没有硬需求涉及"必须对照真实数据/系统校验"的，就必须走 Skill，不能让大模型自己编。
数字和正式文件必须可验证凡是数字、统计结果、正式材料，必须由 Skill 产出或校验，大模型不允许凭空生成。
LLM 负责理解、串联、解释大模型的价值在于把 Skill 的结果转成人话、串联多个节点——不是替代 Skill。
R2/R3 节点无条件确认不管内容是 Skill 产出还是 LLM 生成，涉及研究/业务决策或正式外发都要停下来确认。
先查是否已有 Skill 可复用同一个 Skill 可能被多条任务链路调用，规划新功能前先确认是否需要新建能力，还是复用已有的。
